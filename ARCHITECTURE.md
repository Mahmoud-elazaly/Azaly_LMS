# Architecture

The Hybrid Architecture MVP blueprint governs this project. The optional master prompt and execution roadmap were absent at inventory. The blueprint uses “phase 1.1” in its lab section and “Phase 7” in its delivery plan. Phase 7 is the execution phase and Hybrid v1.1 is the release. Canonical public course details use the locale prefix. The existing HTML stays at its original path outside app and public.

The LMS is a modular monolith. App Router pages, shared UI components and HTTP routes live in `app/`. Identity, authoring and learner policies and services live in `src/features/`. The public catalog query, database connections, scoped command calls, Drizzle schemas and migrations live in `src/db/`. PostgreSQL runs on a private network. Interface strings use next-intl. Course translations belong to individual published revisions. Use native semantic controls and Tailwind styling. Server-side access policies protect learner and staff routes.

Phase 1 serves published catalog metadata and a legitimate empty state. Publishing and authoring arrive in Phase 3. Enrollment and course delivery arrive in Phase 4. Storage, background jobs and lab controller deployment enter only when their feature gates require them.

The development and verification toolchain runs inside Docker. The development service bind-mounts application source and uses a separate Compose project from production. Chromium runs in a dedicated image with a separate test database. Production installs the frozen pnpm lockfile and uses an internal data network for PostgreSQL.

Phase 2 adds Better Auth behind `/api/auth`, with a separate auth database pool and a sanitized session endpoint. Version 0.3.0 closes public registration and moves account provisioning to `/api/admin/users`. The identity module uses scoped PostgreSQL functions for invitation state and audited account changes. Activation consumes a hashed, expiring token and creates the credentials in one transaction. The web service sends invitation messages through the configured mail provider.

Phase 3 keeps authoring in the modular monolith. The bilingual builder submits commands to the authoring API through a separate database login. A scoped PostgreSQL function verifies the active actor session and course ownership before any draft read or write. Instructors can author courses they create. Owners and Admins can work across courses. The public catalog still reads version metadata under its existing read-only role.

The Phase 4 learner module delivers the published snapshot through a dedicated database login and a scoped command. That command checks the live Student session and enrollment ownership, projects only the selected locale, and grades from the private answer key. The public catalog continues to use its read-only pool. The bilingual player keeps presentation and interaction state in the browser while PostgreSQL retains enrollment, resume, bookmarks, progress and grades.

Phase 5 uses the existing authoring and learner connections for the question bank, Guided Labs and reviews. Authoring imports a copy of a question into a draft, and publication stores that copy and the Guided Lab templates with the rest of the snapshot. Learners read localized lab instructions and update progress through their pinned enrollment. A separate authoring command scopes the review queue to the reviewer’s courses and appends the decision. The LMS presents command and starter text for practice in a learner-controlled environment.

Phase 6 ships a curated course package with localized lessons, versioned exercises, and bank questions. The one-off seed command runs in the migration image with the existing deployment database identity. It stages a private draft and its bank entries in one transaction. Staff can publish through the builder, and the seed command can publish the exact curated draft as a first revision. Both paths use the existing catalog metadata, snapshot, and publication event model. The learner practice Compose project is independent of the application.

Phase 7 enables the NGINX Real Lab pilot when the deployment configures a lab bridge. Next.js uses the learner database role to queue jobs and issue ten-second workspace grants. The bridge consumes a grant once through a separate PostgreSQL role and forwards the fixed operation to the authenticated controller. The controller owns Docker access and runs on a dedicated worker VM for deployments. The local Compose profile uses the same components on one host for development and acceptance. The controller runs the versioned checker outside the learner container and returns the two observed criteria to the bridge.

Phase 8 shares a Markdown renderer between draft preview and the learner player. It renders ordinary Markdown as React elements and loads Mermaid on demand for diagram fences. Mermaid runs with strict security and returns an SVG image for the diagram canvas. Pan, zoom, and source fallback live in the browser. The Question Bank adds code-line selection and CLI recall. The learner SQL command projects the visible question fields and grades submissions inside the existing `academy` database.

The Phase 8 importer reads a local Markdown file or structured ZIP and builds the same course document the builder uses. Dry runs validate files and pairings offline. Apply calls a scoped authoring function with a live staff session. Authors use the existing publication action to create a new immutable snapshot. [Importer instructions](README.md#import-a-markdown-course)

Run `bash infra/verify.sh` to exercise the Markdown rendering, scoped import, and mixed assessment grading alongside the preceding phases. [Observed checks](PLANS.md#phase-8--lesson-diagrams-assessments-and-course-import)

Phase 9 adds the learner-only Knowledge Graph and My Mastery routes to the workspace sidebar. Server components and `GET /api/mastery?locale=en` use the same authenticated service. The service reads a fresh evidence snapshot from the single `academy` database through the learner connection and computes scores, six domain summaries, and the remediation order on the server. It derives the learner from the Better Auth session and accepts only a locale. The API response uses `Cache-Control: no-store`.

The graph uses native HTML buttons, an SVG edge layer, and a scrollable canvas with keyboard and pointer panning. Its filters and open concept are encoded in the URL. A concept drawer links to published material in the learner’s pinned enrollment. Learners who still need to enroll go to the published course page. The radar includes a text key for all six domains. No separate service or datastore is required. [Phase 9 gate results](PLANS.md#phase-9--cross-track-knowledge-graph-and-mastery)

## Phase 10 mock interviews

The learner workspace adds `/ar/interview` and `/en/interview`. The `/api/interview` routes read the live Better Auth Student session and check the configured origin on writes. The learner database login calls private interview functions in the existing `academy` database. A short reservation in PostgreSQL protects a session while the server calls Gemini. A second database command commits the result, scoped to the active learner and reservation.

The grounding builder sends localized Knowledge Graph summaries and relevant lesson extracts from published snapshots. It uses an owned enrollment’s pinned publication when available. Without an enrollment it uses the latest public publication in the requested locale. The rubric incorporates role and seniority. Infrastructure as code guidance is marked `[Supplemental]` when the learner selects that scope.

Set `GEMINI_API_KEY` in the server environment to enable generation. Web and dev Compose services pass it to Next.js at runtime. The service uses the Gemini 3.8 Flash REST API, checks the prompt with `countTokens`, and requests structured JSON. Zod validates the response before it reaches PostgreSQL. The learner sees interview history in the workspace and can open linked concepts in the Knowledge Graph. The verification browser uses an isolated loopback Gemini stub. [Gemini model documentation](https://aistudio.google.com/docs/models/gemini-3.8-flash) · [Phase 10 verification](PLANS.md#phase-10--server-side-ai-mock-technical-interviewer)

## Phase 11 production and release hardening

Migration `0012_identity_definer_hardening` assigns the six existing identity routines to `academy_identity_definer` with the table and column grants their operations require. The registration trigger allows that owner to provision staff through the one-use invitation activation routine and continues to protect the active Owner. The single `academy` database, fixed routine search paths, and runtime connection boundaries continue to govern identity and content access.

The auth adapter uses the existing PostgreSQL rate-limit table for a per-identifier sign-in budget across instances. Better Auth retains its per-process address limit. Protected routes use the session and configured origin before reading write payloads. The HTTP layer bounds JSON reads before schema validation. The authoring body cap accommodates the existing document size limit. The web server disables Next.js incoming request URL logging and sends browser capability, framing, and referrer restrictions.

The cumulative gate audits routine owners and grants, builds browser assets with synthetic credential values, and checks both locale directions in Light, Dark, and System mode. The release workflow can create the GitHub Release on a rerun when a previous run pushed the annotated tag before publication failed.
